# Kanban 卡片写作规范

给「人 → 编排者 → 执行者」这条链用的写卡规范。卡片是一次可验收交付的最小单位，
写不好的卡片会在执行者那一侧变成开放式探索，浪费额度且无法验收。

## 何时用

- 要把一件事交给执行者（agent / codex）异步去做
- 需要事后能回答「做到了没有、凭什么说做到了」
- 需要人中途拍板（review 卡）

## 四段式

```markdown
## 目标
<一句话说明要达成的结果，不是要执行的步骤>

## 不做什么
- <明确排除的范围：不要顺手重构、不要动 X 模块、不要升级依赖>

## 验收
- 工作区：worktree:<repo>
- 命令：`<build 命令>`、`<test 命令>`
- 期望：退出码 0；关键输出包含 `<关键行>`

## 证据
- 每条验收命令的退出码
- `git log --oneline -1`（证明存在原子 commit）
- `git diff --stat HEAD~1`（证明改动范围没有溢出）
```

## 好卡 vs 坏卡

坏卡：「优化一下数据加载性能」——没有边界、没有验收、无法判定完成。
好卡：「把 `<模块>` 的加载函数改为批量读取，验收：`<测试命令>` 通过且单次调用次数从 N 降到 1；
不要动其余调用方」。

## 常见错误

- **只写步骤不写目标**：执行者会机械照做，遇到障碍就卡住。
- **验收命令含糊**（「跑一下测试」）：执行者会自选命令并报告通过。
- **不指定工作区**：默认临时目录在任务完成后被清理，产出直接消失。
- **把支撑卡挂到被它阻塞的父卡下**：两张卡永远不会被调度，需在 body 里引用父卡 id。
- **一张卡塞多个交付**：失败时无法部分完成，回滚粒度也变粗。
